# Credo

Credo (Latin: "I believe") is the mentor framework for Claude Code: a self-contained process layer that governs how a whole session runs. It turns a loose set of good habits into an enforced, project-local workflow: a per-session working mode, a work-item lifecycle with a hard Definition of Done, budget-aware autonomy, visual verification, and safety rules that travel into every subagent.

It is opinionated by design and stands alone. Three external touchpoints are documented honestly below: the `limit` plugin (recommended prerequisite for a few features), `tmux` (strongly recommended, needed by the self-compact and self-reload commands) and `ntfy` (optional push notifications). Everything else lives inside this plugin.

## What credo is

credo is built from small, composable pieces:

- **Session modes** - every session runs in one of three modes (active, passive, autonomous). The mode is per session, stored on disk, and re-surfaced on every prompt.
- **Work-item lifecycle** - each task is a Markdown file under `.credo/items/`. The folder the file lives in is the single source of truth for its status. A hard Definition of Done gate controls promotion to done.
- **Definition of Done** - work counts as done only after a dedicated post-completion audit, plus a visual verify for anything with a UI surface.
- **Budget awareness** - one place that governs how much of the 5-hour and weekly API limits may be spent, when to throttle, pause, wake up, or stop.
- **Visual verification** - a UI change is proven by driving the real thing in a browser and measuring computed layout, not by a green test.
- **Safety** - filesystem-protection and no-autonomous-installs rules, doubled into a skill so they apply inside subagents too.
- **Subagent self-sufficiency** - every subagent is primed at start with the load-bearing rules, so delegated work stays correct even if the main agent context has drifted.

## Session modes

The mode is per session and set with a command. It is stored on disk keyed by the session id, so it survives compaction, new sessions, and subagents. The `UserPromptSubmit` hook re-injects a one-line reminder of the active mode on every prompt, and names the matching skill to load. A second hook injects the current local date and time (mode-independent) - on every prompt via `UserPromptSubmit`, and additionally on `PostToolUse` (throttled + delta-guarded) so the clock stays fresh during long autonomous runs instead of freezing at the last prompt. This keeps the agent date/time-aware: when no mode is set it proposes a fitting presence mode via Ask (never autonomous, never silently), and it mentions the active mode in normal output now and then, especially after a long gap since the last prompt. An autonomous run is never interrupted by a mode-change question.

A third `UserPromptSubmit` hook (`credo-skill-nudge.sh`) re-surfaces a single low-cadence self-assess reminder, because the SessionStart knowledge list ages out over a long session and the credo skills get underused. It never forces a skill: the agent is asked to judge by effort and risk and actively use the fitting credo skill (diag / verify / audit / items / requirements-verbatim) on non-trivial or complex work, and skip it on small or trivial changes. It fires in all credo modes. Toggle with `CREDO_SKILL_NUDGE` (default true) and set the cadence with `CREDO_SKILL_NUDGE_EVERY` (default 5); the fire slot is offset by half the window from `credo-attended-reminder.sh` so the two reminders never stack in the same turn.

A `SessionStart` hook makes the session credo-aware. Until the session has made a credo decision, and only on a human-present (re)start (`startup`/`clear`), it asks - via Ask - whether to use the credo workflow (yes runs `/credo:session-init`, no records a marker so it never asks again); it never asks in autonomous work, nor on `compact`/`resume`/`fork`. Once credo is active, the same hook re-injects the full credo command + skill list on every start (including after a compact, when the model context is gone), tagged by execution class so it is clear which commands the agent may run itself, which need the user, and which it must never trigger autonomously. The activation ASK can be turned off on its own with `CREDO_SESSION_START_ASK=false` (the whole hook with `CREDO_SESSION_START_INJECT=false`), and when the task backend is `gsd` the workflow text stays silent, since GSD is then the task system rather than credo. The same hook always appends the model-preset block (the main-agent prompt of the active preset plus a per-spawn rule) and a compact user-shorthand legend (see [Chat shorthands](#chat-shorthands)) - in every state, including declined or `/credo:disable`d directories and the `gsd` backend.

- **active** (`/credo:session-active`) - intensive live collaboration with the user at the keyboard. Progress is logged via the limit thresholds and compact-plus, open GO items are picked up alongside, clarifications happen during subagent waits. No keep-alive.
- **passive** (`/credo:session-passive`) - the agent carries most of the work while the user is reachable only for clarifications. Every item is pushed toward a full GO; less is more, so only genuinely ambiguous items go back to the user. No keep-alive.
- **autonomous** (`/credo:session-autonomous`) - approved GO items are worked unattended. Keep-alive is hook-enforced: a registered Stop hook blocks a stop that has no scheduled ScheduleWakeup and instructs the model to set one (loop-safe, and inert outside autonomy); a registered UserPromptSubmit hook turns autonomy off on any real user message. Budget caps are enforced, ntfy sends immediate come-to-PC pushes (questions, blockers, completion) plus a mandatory content-rich progress digest on a fixed interval, and progress is secured via compact-plus.

Each command sets the mode and loads its skill. The three session skills share one canonical common core (defined in the session-active skill) and layer their mode-specific rules on top.

Owner actions (commands, installs, tests, clicks) are written out in full in the chat reply while the owner is present. Presence follows the last owner prompt. An owner prompt within one hour counts as present, in any mode. While the owner is away, the full write-up is skipped and the action stays open until the first owner prompt after the absence.

### Session roles

Orthogonal to the mode, a session can carry a persistent default role that scopes which part of the item lifecycle it owns. Like the mode, the role is stored on disk keyed by the session id, so it survives compaction and new prompts.

- **plan/clarify** (`/credo:role-plan`) - owns clarifying `1_clarify` items; it does not commit or push.
- **task/build** (`/credo:role-task`) - owns implementing GO items, including commits and push per dogma.
- **none** (`/credo:role-clear`) - clears the role, back to no role, so the agent does everything.

## Chat shorthands

credo teaches the agent a few short chat shorthands, so you can type them without adding anything to your own `CLAUDE.md`. The `SessionStart` hook injects a small legend on every start (`startup`, `resume`, `clear`, `compact`, `fork`), so it survives compaction. It is pure user-intent parsing, not workflow: it applies in every directory - credo active or not, hub directories, directories without `.credo/`, and directories silenced via `/credo:disable`. Each shorthand refers to what precedes it and has a general meaning first, plus a credo-item mapping when an item is named.

| Shorthand | Meaning |
|-----------|---------|
| `dd` | Done. `<thing> dd` = that thing is done; bare `dd` = the last discussed or requested thing is done; `cc-up dd` = the update is done. On a single Definition of Done point, `dd` ticks only that point, never the whole item. For a credo item (`#123 dd`) the agent runs the normal Definition of Done gate (audit, plus verify for `ui: true`) and on a pass moves it with `credo-item-move.sh 123 done`. The shorthand is your statement, never a gate bypass: if the gate fails, the agent reports instead of moving. |
| `vf` | Verified or verify, by context. In a manual test round where you were asked to check something, `vf` means you checked it and it passes. The scope is exactly what it refers to: on a single Definition of Done point only that point is ticked as verified and the item stays where it is; only when the whole item was under test (`#123 vf`) does it move to `3_verified/` via `credo-item-move.sh 123 verified --user-authorized` (main agent only). Otherwise it is an instruction to verify for real with runtime proof, not a code review (in credo: the verify skill, via subagents). If it is unclear which is meant, the agent asks briefly. |
| `cf` | Start or continue a clarify round: structured questions until the open points are resolved. In credo: the `1_clarify` items, one item per Ask round, or the named one (`#57 cf`). |
| `go` / `bk` / `pk` / `ar` | Item moves, valid only right after an item ref (`#57 go`); bare they are ordinary words. `#N go` = your GO approval: the agent adds a `(GO: <your words>)` line to the item History and moves it to `2_go` if the GO entry gate (G1-G6) passes, otherwise reports why not. `#N bk` = block it: the agent asks for the concrete blocker if you did not name one (`blocked_by` is mandatory) and moves it to `3_blocked`. `#N pk` = park on hold, `#N pk future` = park for later. `#N ar` = archive. All moves go through `credo-item-move.sh`. |
| `???` | Explain the thing it follows (or the last thing, when alone) in depth: What / Why / Example / Consequences. Same behavior as `/credo:explain`. |
| `??` | Explain at medium depth: the same four parts, each short (about 66 percent of `???`). Alone, or at the end of any message (`the audit gate ??`, `is that safe??`). Same as `/credo:explain` with level `medium`. |
| `?` | Explain briefly: two or three bullets (about 33 percent of `???`). Same placement as `??`. Same as `/credo:explain` with level `short`. The longest ending wins (`???` before `??` before `?`); a normal question ending with `?` (`Is it done?`) gets this short format. Inside a message each marker applies to the part right before it (`what about xyz ?? and explain zxy ???`). |
| `fastfast` | Speed order, anywhere in a message (`deploy fastfast`, `give me the list fastfast`): the agent does it immediately and skips audits, full test suites, verify runs and detours; only the commit gate and the hard safety rules (safety skill, secrets, no installs) still apply. The checks are caught up afterwards in the item: a History line `fastfast: <what>, <commit>, <deploy>` and an open Definition of Done for the deferred audit, tests, verify and done gate. `deploy fastfast` deploys the current main to the target(s) the project defines (a project rule, for example in `.credo/RULES.md`) through its own deploy path, keeping its gate order; if it is unclear what goes where (stage, prod, both), the target is clarified first. It moves to the front of the build queue; the builder cap and the same-files rule stay, except one extra slot when the case is clearly simple (no overlap with running builders, no migration or shared hot file, small change); in doubt the owner is asked first, and an autonomous run with the owner absent waits for a free slot. The resource gate always stays; its builders run only the relevant tests. Never a way around the workflow. |
| `cc-up` | You fully updated Claude Code (plugins and marketplaces fetched and installed, `/reload-plugins`, full quit and restart, possibly resumed). The running state is current; the agent takes this at face value and never asks for update steps or proof. Also valid when mentioned in passing. |
| `cm` | Commit, following the repo's commit rules. No push. |
| `ph` | Commit and push, following the repo's rules (push only where they allow it). |
| `exclude` / `excluded` | Always the local `.git/info/exclude`, never `.gitignore`. Only `ignore` / `ignored` / `gitignore` means `.gitignore`. |
| `#N` vs `§cct_N` | `#N` only for real items (credo items, issues, PRs, tickets). Claude's harness tasks and any other numbering are `§cct_N` (cct = Claude Code task, e.g. `§cct_2`), so the two never get confused. `§cct_2 dd` = harness task 2 done. |
| Typed codes | Every manual test, every question to the user and every product-visible decision the owner may overrule gets a code (internal process decisions get no veto code) from its own monotonic counter: tests `T1, T2 ...` under `### 🧪 T3) <topic>` (steps numbered; answer `T3 vf`, or `T3.2 vf` for step 2), questions `Q1, Q2 ...` under `### ❓ Q4) <topic>` (answer `Q4: ...`), vetos `V1, V2 ...` under their own heading line `### ✋✋ V2) Veto possible: <what> ✋✋` (answer `V12 <objection>` or `V12 ok`). Numbers are never reused or reset. A veto has no deadline and stays open until it is resolved by code, with `drop all vetos`, or implicitly when the user already accepted that point elsewhere, or the agent closes it itself (item done or verified with nothing of the decision still open, or the decision superseded). Each reply ends with all still-open codes in a language-neutral footer (`**🧪: T3** · **❓: Q4, #177** · **✋: V2, V5**`), so credo's band can show them. The band drops a code as soon as your prompt answers it (`T3 vf`, `V5 ok`, `Q4: ...`, `drop all vetos`), and the next footer replaces the list. The next free number per type survives a compact via the handoff (informational only). Every new number comes from `scripts/credo-code-next.sh` (type T, Q or V, optional count): one locked counter per project, shared by all sessions of it. |

Turn off only the legend with `CREDO_SESSION_START_SHORTHANDS=false`; `CREDO_SESSION_START_INJECT=false` silences the whole hook, legend included.

## The `.credo/` structure

`scripts/credo-init.sh` creates a per-project `.credo/` tree in the target repo (idempotent) and adds the git-exclude lines so `.credo/**` is not committed by default (except `RULES.md`, see below). The layout:

```
.credo/
  docs/                stable "how we work here" conventions
  screenshots/         visual-verify evidence: <task>-<viewport>-<YYYY-MM-DD>.png (a PostToolUse hook files screenshots here automatically, even from a hub)
  items/
    1_todo/{1_clarify,2_go,3_blocked}
    2_done/
    3_verified/        human-authorized; agent files here only on your explicit instruction
    4_archived/
    parked/{hold,future}
  process/
    requirements/      append-only verbatim log
    handoffs/          rolling HANDOFF.md plus handoffs/archive/
    reports/           diag / audit / verification reports
  checklists/          auto-generated cross-cutting checklists
  config               per-project config (YAML)
  id-counter           deterministic integer counter
  RULES.md             per-repo special rules (grants); versioned by default
```

`.credo/**` is deliberately kept out of git, with ONE exception: `RULES.md` (per-repo special rules) is versioned by default, because those rules are meant to travel with the repo. Everything else's persistence across a compact is disk plus your normal backups, not commits.

**Opt-in versioning (per project).** The default (all of `.credo/**` excluded except `RULES.md`) is right for solo or private work. If you want the items and process visible in the team's history, run `credo-init.sh` with `CREDO_VERSION_TRACKED=1`: it then versions `.credo/**` in the repo except the per-project `config` and the `screenshots/`, which stay local always. The exclude entries are kept in a marker-delimited managed block in `.git/info/exclude`, so re-running switches the mode cleanly in either direction (drop the variable to go back to fully unversioned). This is a deliberate per-project decision; the default is unversioned.

### Config cascade

Config is YAML, merged lowest to highest:

```
builtin (templates/config.default.yaml) < global (~/.claude/credo/config) < profile ($CLAUDE_CONFIG_DIR/credo/config) < project (.credo/config)
```

The builtin template ships universal, safe-for-everyone defaults (viewports 320/768/1440, timing windows, the compact thresholds 80/92, the budget schedule, wakeup offsets, 2-4 writing builders per independent area, the 90 % CPU/RAM resource gate, release.auto off, dont_ask_twice off). On first need the global config is created from this template. Personal and environment-specific fields (ntfy topic, commit-identity hint, WSL reachability, living-docs list) are intentionally left empty and are filled just-in-time by the skill that needs them, with permission per change. `/credo:setup` is an optional way to pre-initialize this.

The **profile layer** sits between global and project: `$CLAUDE_CONFIG_DIR/credo/config` (for example `~/.claude-private/credo/config`) lets a second Claude Code profile override the shared global per key, while every key it does not set still falls back to global. It is optional and never auto-created; for the default profile it equals global and is skipped. Session state (modes, decisions, project pins) and the autonomy flags likewise follow the active profile, so two profiles run side by side without sharing state.

### Deterministic id-counter

Item ids come from `scripts/credo-id-next.sh`. The counter file holds the last id given out; allocation is atomic (flock): read the counter, scan the items tree, take `max(counter, highest existing id) + 1`, write it back, print it. The counter, not the folder, decides the number - deleting the highest item never lowers the next id, so a deleted id is never reused; the folder scan is only a safety floor that lifts a counter which fell behind the items on disk (merge, clone, backup restore, sync) and warns on stderr when it does. Always take an id from the helper; never hand-pick one.

## The item workflow

A work item is one Markdown file (`templates/item.template.md`). Its frontmatter is lean and mandatory: `id`, `title`, `created`, `type` (bug | optimization | feature | question | chore), and `ui` (true means a visual verify is part of the Definition of Done). The optional `audit: full` forces the full audit tier (see Audit depth). There is no status field, because the folder is the status.

The lifecycle, moving the file with `scripts/credo-item-move.sh`:

1. **clarify** (`items/1_todo/1_clarify/`) - requirement captured verbatim, success criteria drafted.
2. **go** (`items/1_todo/2_go/`) - GO given; ready to build. A human-owned item (from the user's own words; `clarify_owner: human` or missing) gets its GO only from the user - the move helper refuses it otherwise. An agent-owned item (`clarify_owner: agent`, `parent: <id>` - slices, follow-ups, build questions, audit findings) is decided by the agent decision rule in an autonomous run only (an interactive mode leaves the decision to the user): per the active model preset's mainagent-prompt (see "Model presets"); each decision is logged and reported so the user can veto, and taste, deletions, installs beyond the item's `## Freigaben`, money, safety and changes to the verbatim requirement still go to the user. On entry an item becomes agent-owned. Entry is gated (G1-G6): only a fully clarified, GO'd item with no open build-details or unbuilt-item dependency may enter. Once here it IS buildable by definition (go=go): the building agent never self-skips or self-demotes it for size, UI, or "not sure it is verifiable". A stale-looking body is likewise never a reason to self-skip or demote a `2_go` item (body-freshness invariant). The one sanctioned way back is the **Named-Decision-Test**: a genuine user-only decision surfacing mid-build sends the item to `1_clarify` marked URGENT - never "too big / too hard".
3. **blocked** (`items/1_todo/3_blocked/`) - GO'd but hard-blocked by another, unbuilt credo item (structured `blocked_by`/`blocks` relations). Auto-returns to `2_go` when the blocker is done. Distinct from `parked/hold`, which is for an external dependency. "Too big / too hard" is never a block.
4. **done** (`items/2_done/`) - built and wired, and the Definition of Done gate has passed. A move to done (or verified / archived) and every release also clean up merged worktrees per DOGMA-PERMISSIONS (see "Parallel work: worktrees").
5. **verified** (`items/3_verified/`) - human-authorized. The agent never self-verifies, but may perform the mechanical move on your explicit instruction (`credo-item-move.sh <id> verified --user-authorized`). Raw `mv`/`git mv` of item files is blocked and redirected to the move helper (enforced by `credo-item-move-guard.sh`).

Parked work lives under `items/parked/{hold,future}`; abandoned work under `items/4_archived/`.

The GO gate by clarify owner and the owner flip on entry into `2_go` are tested in `scripts/test-item-move.sh`. The only deletion the move helper does is `scripts/credo-item-move.sh --remove-duplicate <path> --user-authorized`: one duplicate item file (same id, untracked or byte-identical to the other copy) on the owner's explicit yes, nothing else.

`scripts/credo-go-stall.sh [hours]` lists the GO items (`1_todo/2_go`) with no progress for longer than the threshold (the argument, else `items.go_stall_hours`, default 24): file mtime and last History date both older. One line per item with id, age and the last History line; read-only. Every listed item is classified (buildable, Named-Decision, human-only verify, blocked) before any idle report; tested in `scripts/test-credo-go-stall.sh`.

`scripts/credo-item-counts.sh [--json]` prints the item count per status folder of the resolved project (read-only, exit 4 when no credo project resolves), so any renderer can show live counts without knowing the folder layout.

`scripts/credo-item-list.sh [--json] [--per N]` prints, per status folder, the total plus the newest N items (default 15) as id and title (frontmatter `title:`, else the slug); same project resolution and exit codes. `scripts/credo-session-status.sh [--json] [session_id]` prints one session's mode, role and autonomy state (running, paused, next wake) from the per-session state files (read-only, exit 2 when no session id resolves).

### The Definition of Done gate

An item may move to `2_done/` only when:

- the success criteria are observably met and the new code is actually wired in (a caller reaches it),
- a dedicated **audit** subagent (not the builder) has reviewed the work against its stated requirement and Definition of Done and returned a pass,
- for `ui: true`, a **visual verify** has driven the real surface in a browser across the configured viewports and captured screenshot evidence,
- docs are updated in the same change.

#### Audit depth

The audit gate always runs, by a dedicated subagent that is not the builder; only its depth follows risk. **full** (every audit check, current verify evidence) applies to `ui: true` items, security-relevant work (permissions, allow/block hooks, secrets, deletion, installs), writes outside the repo, data migration, large scope (guide value: more than ~10 files or a new component), items with the optional frontmatter `audit: full`, and anything in doubt. **lean** applies to everything else: the diff against each DoD point, wiring of new code, docs current for the change, and stale claims inside the item - still with severity-ranked findings and a verdict. The main agent picks the tier and the report states it with a one-line reason. There is no `audit: lean` override, so a risky item is never downgraded. Builder and audit run dogma's `relevant` test stage when the repo defines one; the full suite runs where dogma places it (for example once per release bundle), not per item. Several lean items may share one audit subagent with one verdict each; full items are always audited singly.

## Building-block skills

Auto-discovered under `skills/`. Each auto-triggers when it applies, including inside subagents.

- **audit** - read-only quality gate; reviews already-built work against its requirement and Definition of Done before it may move to `2_done/`. Proposes a severity-ranked decision (BLOCKER/MAJOR/MINOR/NIT), never a fix.
- **diag** - read-only root-cause diagnosis for a symptom; establishes the mechanism at file:line before any fix. The fix is a separate, GO-gated step.
- **verify** - visual verification as the Definition of Done for any change with a runtime surface; proves behavior in a real browser with computed layout. A down surface may be brought up or restarted autonomously ONLY when the target is positively verified local (a process on this machine, not a deployed/remote/shared environment - judged by where it runs, not by the git branch), via `verify.local_bringup`; otherwise the visual verify defers as human-only.
- **pr-vetting** - rigorous multi-subagent vetting of a pull request across technical, security, value/fit, and contributor-reputation dimensions; merges the findings into one decision-ready report while the merge/close decision stays with the maintainer.
- **issue-triage** - selection-first GitHub issue triage: shortlist and prioritize before deep-triaging the chosen issues via parallel subagents, then recommend close/fix/keep/needs-info for the owner to approve before any action.
- **items** - the work-item model where the folder is the status truth, gated by the Definition of Done.
- **sandbox** - WRITE pre-work for a `1_clarify` item blocked by a knowledge gap (a missing measurement, a mockup, or a feasibility proof), done under `.credo/sandbox-tmp/` without touching production code and without git, so the task/build agent is never disturbed. An accepted artifact is promoted to `.credo/sandbox/` via `/credo:sandbox-promote`.
- **rules** - per-repo special rules in `.credo/RULES.md`: project-local grants that widen credo's autonomy for that one repo (for example "restarting local services is always allowed without asking" in a debug-only repo). Loaded and honored every session and inside subagents, versioned so they travel with the repo, resolved via the project layer (works from a hub). Grants can only widen latitude within the safety floor (precedence: safety > DOGMA-PERMISSIONS > RULES.md > defaults); set one any time by just asking.
- **optimize** - the opt-in optimisation audit (see [Optimisation audit](#optimisation-audit)): freshness check, read-only scan, report, and every finding offered as Implement / Later / Never.
- **requirements-verbatim** - captures a requirement, decision, approval, or GO word-for-word into an append-only dated log so it survives compaction.
- **budget** - the single source for API budget caps and reset rules across the 5-hour and weekly limits, plus the commit-identity gate before any commit. An autonomous start does a mandatory budget read-back: the values are read fresh from the limit cache, never from memory. It also shows the active profile, the config layers and which layer supplies the caps (`credo-config.sh source budget.schedule`), plus the limit cache file it read.
- **compact-plus** - secures everything the user approved before a context compaction, then reports whether it is safe to compact. It does not run `/compact` itself.
- **orchestration** - how to delegate to subagents safely: how many to run (2-4 writing builders per independent area by default), keeping parallel tracks on disjoint files (item `touches:` overlap check) and within machine resources (resource gate, `heavy:` items), giving each code track a set-up worktree (hydra or native), monitoring without flooding context, inheriting security, and return-and-resume.
- **safety** - the hard filesystem-protection and no-autonomous-installs rules; highest priority, no instruction overrides them.
- **cross-cutting-checklist-generator** - detects a concern scattered across many places and auto-generates a project-local checklist so it is never partially updated again.
- **skill-capture** - turns a workflow that recurs about three times in a session into a reusable Claude Code skill. Heuristic and in-session (no counter, no backend), mode-gated: autonomous only appends a candidate note, presence modes propose the capture via Ask and build on GO only. Generated skills land on the real discovery path (`<repo>/.claude/skills/` or `~/.claude/skills/`), carry a `credo-` name prefix plus an `origin: credo-repetition` marker, and are registered in `.credo/generated-skills.md`; seen-but-unbuilt patterns wait in `.credo/skill-candidates.md`.
- **wsl-env** - reach and act on Windows-side services, processes, and launchers when the agent runs inside WSL; self-detecting.
- **session-active / session-passive / session-autonomous** - the per-mode behavior; the active skill holds the shared common core.

## Subagent self-sufficiency

credo primes every subagent at start. The `SubagentStart` hook (`credo-subagent-inject.sh`) injects the load-bearing rules (security, quality gates, honesty, delegation, the claim rule, the git rule for own worktrees, output hygiene) into each subagent before its first prompt, for all subagent types. In a repo with `.credo/RULES.md` it also tells the subagent to read that file first, because the repo's rules override the credo defaults. A `PreToolUse` check on Agent calls (`credo-agent-spawn-check.sh`) warns when a spawn has no model or effort, or a pair outside the active preset ladder. It also injects a fresh, authoritative time (and best-effort live budget from the statusline cache) so a subagent works from the real clock instead of the possibly frozen time/limit values inherited from the main agent's context. This complements the skill descriptions, which are written to auto-trigger inside subagents as well. So even a main agent that only delegates gets correct results, independently of its own context state.

## Cross-profile peer bridge

Cross-session messaging (`ListAgents` / `SendMessage`) only discovers peers that share the same `sessions/` registry, so sessions started under different profiles (different `CLAUDE_CONFIG_DIR`, e.g. `~/.claude` vs `~/.claude-private`) cannot see or message each other by default - even though the inbox sockets live in one shared runtime dir and the transport works across profiles. Because agents talking to each other regardless of profile is part of the workflow, credo bridges this.

The `credo-peer-bridge.sh` hook (SessionStart, UserPromptSubmit, PostToolUse) autodiscovers sibling profiles (`~/.claude*` dirs that own a `sessions/` registry) and mirrors each **live** peer descriptor into the current profile's `sessions/` dir as a **regular file** tagged with an ownership marker (`credoPeerBridge`). That makes cross-profile peers appear in `ListAgents` and become reachable via `SendMessage`. Regular-file copies are used deliberately: the discovery reader enumerates regular files only and does not follow symlinks, so per-file symlinks are legacy v1 and are not honored by the discovery reader.

- **Resume stays clean.** `/resume` reads transcripts under `projects/`, never `sessions/`, so a mirrored descriptor (which has no local transcript) never pollutes the resume picker. Work/private history remain fully separate.
- **Safe by construction.** The hook only ever removes files that carry its own `credoPeerBridge` marker (plus leftover legacy symlinks and its own temp files). A real local descriptor is an unmarked regular file and is never touched or overwritten; it never removes directories and never touches anything outside the profile's `sessions/` dir, and it always exits 0 so it cannot surface as a hook error. Entries whose source session has ended are pruned on the next run.
- **Disable** with `CREDO_PEER_BRIDGE=0`.
- **Caveat:** the descriptor format is internal to Claude Code and undocumented, so a future version may change it. The bridge is fail-safe - if that happens, peers simply stop appearing; nothing is corrupted.

## LAN peer relay (cross-machine, no cloud)

The cross-profile bridge above only reaches sessions on the SAME machine. The LAN relay (`scripts/credo-peer-lan.py`) extends the same peer model to sessions on DIFFERENT machines in one trusted network, without the Anthropic cloud (no Remote Control, no API). A daemon runs on each machine, publishes its local sessions to its configured peers over TCP, and mirrors every remote session into the local `sessions/` registry - so a remote peer appears in `ListAgents` and is reachable via `SendMessage`, with replies routing back over the LAN. One relay per machine serves ALL Claude Code profiles of that machine (`~/.claude`, `~/.claude-*`): every remote session is mirrored into each profile's `sessions/`, the roster names the profile of each local session, and a message reaches a session in any profile. The setup asks which profiles the relay serves (default: all found; `/credo:peer-lan profiles` lists and changes it), and a session in any served profile starts that same relay with the one machine config. A profile it does not serve gets neither a relay nor a config of its own.

A remote session has no local process, so its descriptor would be reaped (the discovery reader validates the pid is a live local process, matching `procStart` = field 22 of `/proc/<pid>/stat` to resist pid reuse). For each remote session the daemon therefore spawns one lightweight local **holder** subprocess that listens on a local **proxy** unix socket and forwards frames over the LAN. The holder is a real live local process, so its pid and `procStart` are real; the mirrored descriptor uses the holder pid as both the `<pid>` filename and the descriptor's `pid`/`procStart`, copies `pidDomain` from a real local session (so it is treated as local), points `messagingSocketPath` at the proxy socket, names it in the mirror naming scheme (below), and carries the marker `credoPeerLan` - NOT `credoPeerBridge`, so the cross-profile bridge never touches it.

- **Dead-simple setup.** On each machine, after `cc-up`: run `/credo:peer-lan init <other-ip> [<more-ips>]`, and under WSL approve one UAC prompt. That is the whole per-machine flow - `init` writes the config token-less, starts the daemon, and (WSL) opens the Windows port in a single elevated prompt. No typed names, no token.
- **Active IP help.** `/credo:peer-lan init` and `whoami` print THIS machine's own LAN-reachable address - the exact value to enter on the other machines - so you never guess which IP. Under WSL that is the Windows host LAN IP of the active default-route adapter (detected via `powershell.exe`, the same reading the relay advertises; excluding the `172.x` WSL IP and vEthernet/host-only adapters); natively it is the default-route source address. `init` and `check` also probe each configured peer and report `reachable` / `not reachable`.
- **Which IP to enter.** Always the TARGET machine's LAN IP: for a WSL2 target its WINDOWS HOST IP (not the `172.x` WSL IP), for a native Linux target its own LAN IP; the source machine's type is irrelevant.
- **Address-based routing (no name contract).** A peer is identified by its ADDRESS (`host:port`), never by a name. `peers[]` is a simple list of `"IP"` / `"IP:PORT"` strings (multiple entries = multiple machines); the legacy `{name, host, port}` object is still accepted and normalized. Routing pairs an inbound roster with the configured peer address it came from, so there is nothing to keep in sync and no "peer silently never appears" footgun. The mirrored peer is named `` `harness`--`network`--`device`--`user`--`profile`--`session`+sid-short `` (for example `` `Claude Code`--`Home WLAN`--`box-1`--`alice`--`.claude`--`My Session`+a-e-4-8-d8 ``): case, spaces and dots are kept, empty parts are dropped, the name before `+` is capped at 150 characters (the session part is trimmed), and the sid short form (first character of each id group plus the id's last character) keeps same-named sessions apart. The sender announces `harness`, `network` (its bound network label), `user` and `profile` (config dir name) in its roster; a loopback sender without a network gets this machine's label. The `session` part is the name the sender announces for the session, chosen in one fixed order (see "Peer names" below); the old harness-derived (cwd-based) name is no longer announced, so a session nobody named shows its tmux session or short id instead. An inbound roster from an address not in the config is still served token-less (the receiving session's consent gate is the protection) and logged once as unexpected; a correctly configured setup never warns.
- **Mode-agnostic by design.** The injected envelope NEVER carries a `from-mode` attribute; the receiving session applies its OWN consent gate. The relay only carries name, body, and reply address.
- **Return channel (one-way reachability).** When only one machine can connect to the other (router behind router, NAT), the side that CAN connect opens one persistent link and rosters plus delivers flow both ways over it - holders hand their delivers to the local daemon so replies use it too. At most one channel per peer pair (simultaneous opens: the link opened by the machine whose `this_machine` sorts lower survives, a random nonce breaks a full tie; only between links that prove, by a per-link secret sent only on that connection or by the pairing key, that they come from the same peer), idle links are pinged and a dead one is dropped after about three roster intervals (capped at 60 s) and reopened. Gates are unchanged: inbound source allowlist, token check on every frame when a token is set, outbound gate for opening; an inbound link may only stand for a reachable configured peer when it comes from that peer's IP and this side keeps its own outbound link to that peer, inbound links are capped (the WSL gateway at `max(2, len(peers))`), and holders for peers outside the outbound allowlist never connect directly. Without a link the relay falls back to fresh connections; an older relay is marked "no link support" after 3 unanswered attempts. Details: [`commands/peer-lan.md`](commands/peer-lan.md#return-channel-one-way-reachability).
- **Per-peer pairing keys (automatic, trust on first use).** All peers share one token and under WSL NAT every inbound link arrives from the same gateway address, so neither tells peers apart. Each relay installation therefore has a persistent random peer id and a static Diffie-Hellman key pair (RFC 3526 group 14, stdlib only) in `peer-lan-keys/` next to the config (0700 dir, 0600 files, atomic writes). On the first link between two relays both derive the same pairing key from the exchanged public values and store it for the other's id and address; the key itself is never sent or logged. Every later link proves the key against a fresh challenge from each side (bound to the id the opener expects at the address it dialed), frames on it carry a sequence-numbered MAC under a per-link session key, a paired peer's address (slot) goes only to a link that proves its key, also while the peer is offline, and a paired peer never falls back to token-only. A paired peer is bound to one address and never re-bound silently (a proven move from a new allowlisted address follows the pairing, logged once; `CREDO_PEER_LAN_FOLLOW_ADDRESS=0` turns that off); a new pairing is stored only after the full handshake. Inbound delivers are verified with the token when one is set. Trust on first use: link each pair of machines once on a network you trust; older relays (or the Codex peer) keep working token-only as before. A new id at a paired slot (reinstall, lost keys) or a paired peer at another address is refused and shown as a pending repair (`pairs`, `check`, session-start hint); `credo-peer-lan.py pair-reset <peer>` accepts it - the only manual step. The pairing record is copied into the keystore of every profile of the machine, so each profile can grant trust to that peer itself; trust is never copied. Details: [`commands/peer-lan.md`](commands/peer-lan.md#pairing-keys-automatic-trust-on-first-use).
- **Optional shared token.** Transport is line-based JSON over TCP. The shared `token` is OPTIONAL. Left empty or omitted, the relay runs TOKEN-LESS - the casual default for a trusted home LAN: it signs nothing and accepts unsigned frames, so any device that can reach `listen_host:listen_port` can message your sessions (gated by the receiving session's own harness consent prompt - the relay never forges a sender's permission mode, so that harness gate stays in place; credo's trusted peers below are a separate local opt-in that needs a paired sender). Set the SAME non-empty token on every machine and frames are signed and verified with HMAC-SHA256, and anything that does not verify is rejected - this restricts messaging to your own devices and is recommended on untrusted or company networks. Enabling it later is just adding the same `token` to the config on every machine; no code change.
- **Safe lifecycle.** The daemon only ever removes descriptors carrying its own `credoPeerLan` marker, plus the proxy sockets and holders it created; on SIGTERM it removes all of them. A stale descriptor from a dead run (holder pid gone) is pruned on the next start.
- **Single instance.** The listen port is the single-instance lock: a second daemon on the same `listen_host:listen_port` fails to bind (EADDRINUSE), logs that another daemon is already listening, and exits 0 without disturbing the running one.
- **Reset (disconnect-all).** `credo-peer-lan.py disconnect-all` (the slash command `/credo:peer-lan disconnect-all`) forgets every other device this machine knows - pairings, trust grants, stored peer addresses and LAN mirrors in every served profile - and restarts the relay, so pairing can be set up cleanly again. It lists what goes and asks first (`--dry-run` only lists, `--yes` skips the question after a confirmation); `--full` also removes the Windows-side setup under WSL. Your identity, bound networks and profiles stay. Details: [`commands/peer-lan.md`](commands/peer-lan.md).
- **Auto-start.** Once the config exists the relay starts automatically on session start via the `credo-peer-lan-autostart.sh` SessionStart hook, detached so it never blocks the session, and only one daemon runs per machine. Disable the auto-start (and the relay) with `CREDO_PEER_LAN` set to `0`/`false`/`no`/`off`.
- **Off by default.** It is a no-op until a config exists at `~/.claude/credo/peer-lan.json` (create it with `/credo:peer-lan init`, or override the path with `CREDO_PEER_LAN_CONFIG`; see `scripts/peer-lan.example.json`). Disable globally with `CREDO_PEER_LAN` set to `0`/`false`/`no`/`off`.
- **Cross-machine networking.** How a LAN peer reaches the daemon depends on the platform; the port used below must always match `listen_port`.
  - *WSL2 (default NAT mode):* the WSL daemon is not reachable directly - the WSL instance is behind a NAT only the Windows host sees, and its IP changes on every WSL restart. `scripts/credo-peer-lan-winproxy.ps1` makes this self-healing. `/credo:peer-lan init` runs it for you as a single elevated UAC prompt (deriving the installer's `\\wsl.localhost\...` path with `wslpath -w` and launching it via `Start-Process -Verb RunAs`); to run it by hand it is ONCE per machine in an elevated Windows PowerShell with `-Install -Port <listen_port>`. That copies the script to an admin-only `%ProgramData%\credo` folder, creates the allowlist-scoped inbound firewall rule, registers a scheduled task that re-applies the `netsh` portproxy (Windows-LAN-IP:PORT -> current WSL-IP:PORT) at Windows startup, and refreshes once immediately. Afterwards it is automatic: the task runs at boot, and the `credo-peer-lan-autostart.sh` hook triggers the same task on demand each time the relay daemon starts, so the WSL-IP-change problem is handled with nothing manual afterward. This elevated one-time step is required on EVERY machine including remote ones and cannot be done remotely. `-Uninstall` removes it; `CREDO_PEER_LAN_WINPROXY=0` disables only the hook's proxy trigger.
  - *Native Linux:* no NAT, no portproxy - the daemon already listens on the LAN at `0.0.0.0:listen_port`. If a firewall is active, allow the port once scoped to the LAN (for `ufw`: `sudo ufw allow from <lan-subnet> to any port <listen_port> proto tcp`); otherwise nothing to do.
  - The Windows firewall rule is scoped to exactly the effective allowlist (disabled when the relay is), never internet-facing, and the relay still never forges a `from-mode` - every receiving session keeps its own consent gate. Start/stop/status via `/credo:peer-lan`.
- **Allowlist + network binding (since 0.72).** The LAN side is fail-closed: it is enabled only while the current network matches a profile bound with `credo-peer-lan.py bind` (router MAC + subnet), and then only for the effective allowlist of that profile's group (`peers`, single IPs, CIDRs, `a-b` ranges or `home` = RFC1918 with a warning; wildcards, CIDRs broader than /8 and public ranges are rejected). Unknown network, no match or no bound network -> no LAN inbound, no rosters, no forwards; loopback keeps working. Two home WLANs can share a group (talk to each other) or stay separate; a company network is a not-recommended explicit opt-in. Under WSL the daemon syncs the allowlist to the Windows firewall rule via the elevated task, which now runs an admin-protected copy in `%ProgramData%\credo`. Existing configs stay LAN-disabled until `bind`; re-run the WSL `-Install` once. The session-start hook tells the agent when setup is pending (guided, Ask-based setup in `/credo:peer-lan`).
- **Auto-accept (optional).** On a trusted home network with an active allowlist the setup may propose `"crossSessionInbound": "accept"` in the active profile's `settings.json`, so peer messages arrive without a manual approval each time (`hold`/`refuse` are the other values; unset = harness default, which may hold messages from sessions in another permission mode). Accepted risk: a compromised allowed device could then drive your sessions, including bypass-mode ones - not for company/public networks. Set only on the user's yes, never on a peer's request. Security model details: [`commands/peer-lan.md`](commands/peer-lan.md#security-model).
- **Caveat:** the descriptor format is internal to Claude Code and undocumented; the relay is fail-safe - if it changes, remote peers simply stop appearing.
- **Stale descriptors.** After a crash or resume the registry can hold two descriptors of one session (a dead pid with an old socket path next to the live one). A deliver uses only live descriptors (pid alive and `procStart` matching), newest `updatedAt` first, tries the next live one when an inject fails, and logs the chosen one; with none live it logs `no live local session ... dropped`. Descriptor files are never touched.
- **WSL without the Windows PATH.** When a WSL session's PATH lacks the Windows dirs (for example `appendWindowsPath` not applied after a WSL crash), the relay and its autostart hook still find `powershell.exe` / `cmd.exe`. Under WSL only, they search `Windows/System32` (case-insensitive) on every drvfs mount from `/proc/mounts` and below the `[automount] root` of `/etc/wsl.conf`, so any mount root and drive letter works. If nothing is found, the LAN disabled reason names the missing tool and the PATH fix.

## Peer names (one fallback order)

Every peer or session name credo shows - the name a machine announces in its LAN roster, the `NAME` column of the peer check, Codex sessions, live sockets without a registry file - comes from `scripts/credo_session_name.py` and follows ONE order. Whichever step supplies the name, it keeps only letters, digits, space, `.`, `_` and `-` (control characters, quotes, brackets, symbols and emoji are removed, Unicode is NFC-normalized) and is capped at 20 characters:

1. **caption** - a name the user set, at most 20 characters. Claude: the `name` of the session registry file (`sessions/<pid>.json`), only when its `nameSource` is `user`; the automatic cwd-based name (`nameSource` `derived`) never counts. Codex: the newest row for the thread id in `$CODEX_HOME/session_index.jsonl` (`thread_name`; a thread nobody named has no row). The index is read defensively: opened without following a symlink, must be a regular file owned by you, only its last 256 KiB are scanned, the name is stripped of control characters and capped.
2. **kitty label** - the title of the kitty tab (at most 20 characters) that holds the session's terminal window (needs kitty remote control: `allow_remote_control` plus a `listen_on` socket; `CREDO_KITTY_SOCKET` and `CREDO_KITTY_BIN` override the discovery; the signal plugin's `[AI...]` / `[ASK]` / `[FIN]` tab prefixes are stripped).
3. **tmux label** - the name of the tmux session the session runs in (at most 20 characters). The tmux pane and client lists are reused for 15 seconds, and one lookup spends at most about 2 seconds in kitty remote-control calls in total, so the roster tick stays cheap. An unnamed Codex thread takes a tmux label only when exactly one Codex pane is free and exactly one thread is unnamed; otherwise it keeps the short id.
4. **short id** - the first character of each session id group plus the id's last character, for example `a-e-4-8-d8`.

A session that Claude Code moved into its background daemon has no tmux or kitty ancestry of its own; its labels come from the client TUI that hosts it (the same verified link `self-compact` and `self-reload` use; when it cannot be verified there is no label). The shown name is display text only: it never takes part in routing or any permission decision. Trust (LAN trusted peers) uses only step 1, the user-set caption, and only as the sending relay resolved it from its own session registry - never a kitty, tmux, derived or id name and never the free-form `from-name` (see `commands/peer-lan.md`, Trusted peers).

## Peer check (absent from ListAgents is not down)

`ListAgents` only shows descriptors in this profile's `sessions/` registry. A Codex session appears there only as a LAN relay mirror (it vanishes while the Codex relay or the credo relay is down), a session of another profile only through the peer bridge, and a session whose descriptor is gone not at all - while the process keeps running in its tmux pane. **Never report a peer as down only because ListAgents does not show it.** Run the peer check first:

```
scripts/credo-peer-check.py            # table + warnings
scripts/credo-peer-check.py --json     # machine-readable
scripts/credo-peer-check.py --no-lan-check   # skip the relay reachability probe
```

It is read-only (no message is sent, no inbox socket is opened, no file is written) and lists every channel side by side. These are Claude sessions from the profile registries, Claude inbox sockets in BOTH candidate socket dirs (`$XDG_RUNTIME_DIR/cc-socks` and the `/tmp` fallback), LAN relay mirrors, the Codex relay (`codex-peer.py list`, whether its port listens, the tail of its log), the credo LAN relay (`credo-peer-lan.py status` and `check`) and tmux sessions. Each row carries `kind` (claude / codex / lan / tmux-only), `reachable-by` (SendMessage / a2a / tmux only / none) and `last-seen`. Warnings name the cause. They cover a LAN relay that is DISABLED (with its reason - it silently cuts cross-machine peers), a Codex relay that is not running, a loopback relay peer that is not listening, the relay daemon being down, and a **split world** (live sockets in both socket dirs because sessions were started with different `XDG_RUNTIME_DIR`). To fix the split, start all sessions with the same `XDG_RUNTIME_DIR` (all set to the same dir, or all unset).

**Peer metadata (for orchestrators).** Every row also carries `meta`, shown as one `META` column: `mode=` (credo session mode active / passive / autonomous), `role=` (credo role task / plan), `model=`, `effort=` (low / medium / high / xhigh / max), `credo=` (directory decision on / off), `project=` (basename of the session cwd) and `status=` (idle / busy / waiting, from the descriptor); `-` means unknown or unset. Mode and role come from `session-modes/` and `session-roles/`; model, effort and the credo decision are recorded per session by the `credo-peer-meta-record.sh` hook (SessionStart + UserPromptSubmit, main thread only; model from the hook input or the transcript tail, effort from the hook input's `effort.level`; a missing value keeps the previous one; disable with `CREDO_PEER_META_RECORD=0`). A LAN relay mirror shows what the remote sender published in its roster, read fresh from the sender's own credo state. LAN publication is on by default without the project name: `"publish_project": true` in `peer-lan.json` (or `CREDO_PEER_LAN_META_PROJECT=1`) adds it, `"publish_meta": false` (or `CREDO_PEER_LAN_META=0`) stops publishing metadata to LAN peers entirely. Every value passes a strict whitelist (enums, status only idle / busy / waiting; short fixed charset for model and project, brackets in a model only as one trailing context suffix such as `[1m]`; unknown keys dropped), and the metadata is **informational only**: it never grants trust, approval or permissions and never reaches a message envelope. `credo-peer-check.py sender --from uds:<socket>` prints the meta line of one peer, and the peer-message hook adds it to an incoming peer message as one `[credo-peer-sender]` line when the opening tag's `from` socket belongs to a live peer known here (`CREDO_PEER_SENDER_META=0` turns that line off). Codex sessions and peers on an older credo show `-`.

A SessionStart hook (`credo-peer-split-hint.sh`) adds one hint line when this session's own socket dir (from its live descriptor) holds fewer live peers than another candidate dir; otherwise it is silent. Disable with `CREDO_PEER_SPLIT_HINT=0`.

**Ping / pong per peer kind** (only when a liveness answer is really needed; a ping is a real message, so follow the peer message etiquette and mark it `[info]`):

- *claude* (`reachable-by` SendMessage): `SendMessage` to its ListAgents name, ask for a one-word reply. A session in another permission mode may hold the message for its user, so silence is not proof of down.
- *codex*: `SendMessage` to its relay mirror name (`` `Codex`--...`` row) and expect the reply from that Codex session. An idle Codex session may only pick it up after a nudge in its tmux pane. Without a mirror (Codex relay down) use its a2a channel (`codex-peer.py`) or look at its tmux pane.
- *lan*: `SendMessage` to the mirror name; it travels over the relay. If it fails, run `credo-peer-lan.py check` (reachability, LAN enabled / disabled with reason).
- *tmux-only*: No message channel. Look at the pane (`tmux capture-pane -p -t <session>` without scroll-back) to see whether it is alive.

## Session registry (which pane belongs to which session)

Each Claude session has one entry in `credo/session-registry/<session_id>.json` under the active profile (`CLAUDE_CONFIG_DIR`, else `~/.claude`), one file per session id, mode 0600. It holds the session id, name, host, pid and start time, the credo mode, the tmux socket and pane (only when the process tree confirms the pane), and an `updated` time. The `credo-session-registry.sh` hook (SessionStart and UserPromptSubmit) writes it and rewrites only on change; SessionStart drops entries of gone processes older than a day. Disable with `CREDO_SESSION_REGISTRY=0`.

`credo-session-registry.py resolve <session-id|name> [--json]` re-checks the entry against the live process: the pid and start time, the session descriptor, and the pane (exists, not dead, still owned by the session). It prints `live` or `stale` with the reason and exits 0 for live, 1 for stale, 3 when nothing or more than one session matches. `credo-session-registry.py list [--json]` shows every entry with its verified status; `--all-profiles` reads every profile under `~/.claude*`. Entries hold no environment values or secrets, and nothing is routed by a stale entry.

## Type-as-owner (send a message or an answer into a session pane)

`credo-owner-type.py` (`scripts/credo-owner-type.py`, logic in `scripts/credo_owner_type.py`) types the owner's text, or an answer to an open question, into one of the owner's own Claude Code sessions, as if the owner typed it in that pane. A local connector (for example a phone app) is the intended caller. The target is looked up in the session registry and must be live, with a pane that still belongs to the session; a stale, unknown or ambiguous session is refused.

- `send --session <id|name> (--text T | --stdin) [--force-append] [--dry-run] [--json]`: the input field must be empty (a busy session is fine: Claude Code queues the text). The whole text is loaded into a named tmux buffer and pasted into the pane in one bracketed paste (`load-buffer` and `paste-buffer -p -d`), so a line break stays a line break inside one message. After a settle of 0.5 s the pane is checked up to five times, 0.5 s apart (item 160): a recognised dialog on the last check holds back Enter, and a pane stop (see the exit codes below) holds it at once; `pane-changed`, `unknown-state` and `input-not-visible` are retried and do not hold back Enter, so when the last check shows neither a recognised dialog nor a pane stop, Enter is sent. A clear check ends the checks early. The field is then checked once: empty again means `delivered`; still holding text means `unconfirmed` (exit 4). The text is not checked character by character before Enter: a paste placeholder such as `[Pasted text #1 +3 lines]` or any other rendering of the field is accepted (owner decision, Q56).
- `send --force-append`: `" " + T` is pasted at the end of the text already in the field, then Enter is sent. The existing draft is sent together with the appended text and is never changed by the tool. The cursor must be at the end of the field (a paste lands at the cursor). No digest is needed; `--expect` is accepted for compatibility and not checked.
- `show --session <id|name> [--json]`: prints the whole dialog block of the open prompt verbatim (every non-blank row from the box top rule to the footer: the command, description rows, every question row, the review answers), each row prefixed with `| ` so that agent text cannot fake the end marker, then the cursor and the digest (sha256 over exactly those rows, whitespace normalized). The cursor, the checkbox and tab states, the typed text of the "Type something" row and the footer are not part of the digest: the answer itself changes the first three, and the footer's key hints follow the highlight. Read only.
- `answer --session <id|name> --ask <spec> --expect <digest> [--persist]`: only while an Ask box, a review page or a permission prompt is open. `<digit>` (1 to 9) selects and sends; `<label>` maps to its option (case-insensitive, must be unique); an option above 9 is reached with Down/Up, the highlight is read again right before the Enter or Space, and a digit is never sent as the text "10"; `esc` declines; `free:<text>` moves to the "Type something" row and types the text (the row must be empty before, and the highlight must stay on that row for every piece); `multi:<d,d>` sets exactly these boxes of a multi select (options above 9 by navigation and Space), then Right and the review. A permission prompt takes a digit or `esc`. The review page takes `1` (Submit answers), and the tool checks that its first option is "Submit answers" first; the review page is bound by its own digest.
- Digest binding: every answer needs `--expect <digest>` (dry runs too) with the digest that `show` printed for the prompt the owner read; without it the answer is refused. The prompt is read again before every key, and no key is sent once it no longer matches. Two prompts with the same options but another command, another description row or another question row have different digests. A prompt answered and then replaced by another prompt of the same kind is reported `answered`; an identical prompt that comes back is reported `unconfirmed` (exit 4).
- Dialog top and scrollback: dialogs are read from the capture with its scrollback (`capture-pane -p -e -N -S -500`; `CREDO_OWNER_TYPE_SCROLLBACK_ROWS` overrides the 500 rows, for tests). The box top is the topmost rule above the question, in the current turn (after the last footer or input box), whose next row is the Ask header or the permission title. A second rule row inside the block (a rule drawn inside the command or the question, or a transcript rule above the box) refuses the box: the owner answers it in the pane. A box whose top is not in view (no row above it in the capture, or no scrollback at all) is refused with `dialog-does-not-fit`. Measured on tmux 3.2a: `-S -500` returns the scrollback rows above the visible area, the visible area is the last rows of the result, and the visible capture must end the scrollback capture (otherwise the pane changed and nothing is typed).
- Invisible and bidi characters: a dialog block that holds a Unicode format character (category Cf: bidi overrides and isolates, zero-width and other invisible characters) is refused by `show` and `answer` with `invisible-characters` ("dialog contains invisible/bidi characters, answer at the PC"). Typed text with such characters, or with control, separator or U+2028/U+2029 characters, is refused with exit 2. The limit is 4000 characters.
- `--persist` is an allow-list. Only a permission option whose full label (the label plus the rows under it, trimmed, case-insensitive) is exactly `Yes` or `No` runs without it. Every other option needs `--persist`: "Yes, and don't ask again ...", "Yes, and never ask again ...", a label that wraps onto a second row, and the explained "No, and tell Claude what to do differently (esc)" (answer `esc` for that one). The result and the log name the chosen option label.
- Tabbed boxes (several questions in one Ask box, measured on Claude Code 2.1.316): answer one question per call. A digit answer moves on to the next question; the last one leads to the review page, which is then submitted with `answer --ask 1`. In a tabbed multi select, `multi:` toggles the boxes and presses Right, which moves on to the next question. The review lists a multi answer in the order the boxes were checked, so the labels are compared as sets.
- Free text and semicolons: tmux drops a trailing `;` of a `send-keys` argument (measured on tmux 3.2a; `--` does not help). Free text is therefore sent as one argument per piece with every trailing `;` as its own `\;` argument, which types `;` (measured). A `send` does not need this, because it pastes the whole text.
- Refused, with nothing typed: an Ask box, review page, permission prompt, slash-command menu, picker or unknown dialog is open, the input holds text without `--force-append`, or the cursor is not at the end of the field for `--force-append`. A dialog counts only as the last block of the pane. Dialog-shaped rows drawn above a visible input box (a dialog footer: "Esc to cancel", with its "·" hints) make the pane unknown (fail closed). Another box drawn below the input box makes it unknown too. A numbered owner message is transcript, not a dialog.
- Before the Enter of a `send` the pane is checked again: a dialog that opened after the paste would receive the Enter and answer itself with its default option, so Enter is not sent in that case. Recognised dialogs are an Ask box, a review page, a permission prompt, a menu or picker below the input box, and a dialog that does not fit or holds invisible characters; the result code is `dialog-after-paste`. The text is taken back out of the field only when the field was empty before the paste and then shows exactly the text, or one paste placeholder (one BSpace removes it); a field holding anything else, or a dialog still open, is left as it is. The result and the log say whether the text was taken back (`taken_back`).
- Checks after a paste, one code per stop (logged as `checks=`, categories only, never text): `dialog-after-paste` (a recognised dialog), `pane-changed` (the two captures of one read differed, e.g. a spinner row), `unknown-state` (an input box with something unrecognised around it), `input-not-visible` (no input box drawn), and the pane stops `owner`, `owner-mismatch`, `pane-missing`, `pane-dead`, `copy-mode`. Only the pane stops and the recognised dialog hold back Enter; the three retried codes do not, and a last check that shows one of them sends Enter (owner decision Q56, best effort). A last check that still shows `unknown-state` or `input-not-visible` therefore sends Enter into a pane that was not recognised (the trade-off of the best-effort decision).
- `--dry-run` checks everything and sends nothing; `--json` prints the result as one JSON object (with the chosen option label).
- Exit codes: 0 delivered, answered, shown or dry-run; 1 refused or failed; 2 usage error; 3 session unknown or ambiguous; 4 sent but not confirmed. After exit 4 check the pane before sending again: the text may already have been submitted.
- Result codes of a `send` (`code` in the result and the log): `delivered`; `unconfirmed` (exit 4); `dialog-after-paste`, `owner`, `owner-mismatch`, `pane-missing`, `pane-dead` and `copy-mode` (exit 1, Enter not sent, the text is in the field unless `taken_back` says otherwise); `paste-failed` and `enter-failed` (exit 1). The retried check codes are listed under the checks above.
- Only the same OS user can use it (the pane process must belong to this user). Every attempt is appended to `<profile>/credo/owner-type.log` (time, session id, mode, character count, result, refusal code, option label; owner-only file, never through a symlink, never a FIFO). The message text is written there only with `CREDO_OWNER_TYPE_LOG_TEXT=1`. If the log cannot be used, nothing is typed.
- Binding is not replay-proof on its own: the digest binds content, not the session or the time. The connector binds every reply to the session and to a short time window, and must show the owner the `show` output before it sends a digit.
- Measured: a two-line paste (tmux `paste-buffer -p`, LF turned into CR by tmux) arrived in the input of Claude Code 2.1.316 as two rows of one input box and was submitted as one user message (live probe on a throwaway session on a private tmux socket). Layouts were measured on Claude Code 2.1.316 only; a different version or footer falls back to refusal, not to guessing.

Known residuals (documented, not closed):

- Race: a dialog that opens between the last check and an Enter can still receive that Enter. The window is one capture and one key press.
- Post-paste checks: an unrecognised state that persists through all five checks (for example a box the classifier does not know) receives the Enter, by design (owner decision Q56). A dialog that opens after the last check is not seen (same race as above).
- Scrollback bound: a dialog whose real top lies more than 500 rows above its visible bottom is not verifiable. If the command inside it reproduces a box structure (a rule row followed by a title row), the detector reads the crafted box from its own top. Only the visible pane and the 500 rows above it are inspected.
- Turn boundary: the top search starts after the last footer or input box in the capture. A markdown horizontal rule in the same turn, above a dialog, refuses the dialog (fail closed; answer it at the PC).
- No scrollback: a capture without rows above the visible area (a fresh session whose output has not scrolled yet, or the alternate screen) refuses every dialog. Reading it would mean guessing where the box starts.
- Enter after a paste is not checked against the text: a paste placeholder hides it, and the owner accepted that. The only check after the Enter is that the field is empty again.
- Permission layouts: only the Bash layout (title, dashed separators, question, options) is recognised as a permission title. Other permission layouts (for example file edits) are not measured and are refused until they are measured.
- Unicode: a legitimate format character (for example a zero-width joiner inside an emoji sequence) in a dialog or in typed text is refused. The check is fail closed.
- The self-restart and wake typing path (`credo_pane_wake.type_text`) still types character pieces: the same tmux `;` behaviour applies there and is not changed by this round.
- Limits: the check is a pane-level one, not a permission check on the caller. An agent with Bash access in the same OS user can run the same CLI or `tmux send-keys` itself, so the OS user is the boundary. A permission answer approves what the prompt shows; the caller must show the owner the command before the answer is sent. `--text` puts the message in the process list; a connector should use `--stdin`.

## Self-restart (resume the same session)

`/credo:self-restart` (`scripts/credo-self-restart.py`) lets a session restart itself - typically to load plugin updates - and come back as exactly the same session in the same profile, continuing on its own with a wake prompt.

- **Owner rule (hard guard in `run`).** Outside credo autonomous mode a self-restart runs only after the user's explicit yes via the Ask tool (`run --user-confirmed`) - an unannounced restart could discard a prompt the user is typing. In autonomous mode it needs no Ask, but is announced at least 5 minutes ahead (`--announce`, default and minimum 300 s) with an ntfy push and a transcript line naming the reason and the cancel command; `cancel` stops it during that period, `status` shows pending/cancelled/relaunched with the scheduled time. Anything else is refused with exit 3 and nothing is started.
- **Profile-safe.** Session id from `CLAUDE_CODE_SESSION_ID`, target = the Claude ancestor process, config dir = the target's own `CLAUDE_CONFIG_DIR`; the transcript must exist in that profile (exactly one match), never a `--continue` or cross-profile fallback; refuses when another process holds the same session.
- **Same flags, same mode.** The relaunch reuses the original (alias-expanded) argv from `/proc` with `--resume <id> <wake prompt>`, and the `credo-permission-mode-record.sh` hook lets it restore a permission mode changed during the session (never escalating).
- **Relaunch methods.** Same tmux pane, else a new Windows Terminal tab (WSL), else a new terminal window (Linux GUI); none -> it refuses. A "Resume from summary" dialog is avoided (the wake prompt is always passed) and answered with Escape as a fallback.
- **Optional plugin update** (`run --update`): only marketplaces in `self_update.marketplaces` (default: credo's own marketplace), versions before -> after in the log, marker and wake prompt. Never touches `autoUpdate`.
- **Restart survival.** `scripts/credo_runtime.py` keeps working state alive across a restart. `keep` (called by compact-plus and before every self-restart) copies the session scratchpad into `.credo/process/runtime/<session>/` with a manifest. `service` keeps a restart list of background services, each in its own detached tmux session `credo-svc-<name>` when tmux is used, else `systemd-run --user`, else nohup. `pane` names tmux panes as `session:window.pane (purpose, last %ID)` and resolves them by name before use; SSH panes are flagged. The SessionStart check after a restart reports services that are not running, SSH panes the user must reconnect (tmux only), and the scratchpad snapshot once. Handoffs resolve plugin paths by glob, never by version.
- **Safety net.** Failures send an ntfy push; before restarting, the agent asks a reachable peer session to send a wake message after ~1 minute. Never while background subagents run. Details: `commands/self-restart.md`.
- **Idle guard (tmux).** Before stopping a session in a tmux pane, the worker waits until the pane is idle with an empty input field and no dialog open (`scripts/credo_pane_guard.py`, two probes); it never stops while the user is typing and gives up after `CREDO_SELF_RESTART_IDLE_TIMEOUT` (default 30 min) with an ntfy push.

## Self-reload (plugin update without a restart)

`/credo:self-reload` (`scripts/credo-self-reload.py`) is the first try after a plugin update; the full restart (`/credo:self-restart --update`, cc-up) is only the fallback. A detached worker optionally runs the allowlisted plugin update (`--update`), then types `/reload-plugins` and `/reload-skills` into the session's OWN tmux pane - each only into an idle pane with an empty input field and no dialog, verified before Enter, and the next key only after the command's `Reloaded` result line (or its timeout). The reload commands do not start a model turn, so it then types `.` to wake the session. A UserPromptSubmit hook consumes the wake file on the next prompt, which cancels the 60 s fallback re-send of the `.` (bounded, only while the pane is idle), and injects a note: loaded vs newest installed credo version and the instruction to fall back to `/credo:self-restart --update` only if the reload was not enough. No background work of any kind blocks it. Owner rule like self-compact. Details: `commands/self-reload.md`.

## Self-compact (the real /compact after compact-plus)

`/credo:self-compact` (`scripts/credo-self-compact.py`) runs the real Claude Code `/compact` on the same session after `compact-plus` secured its state, to save tokens. A detached worker types `/compact Afterwards reload <handoff> ...` into the session's OWN tmux pane (verified to belong to this Claude process, on this session's tmux server) - only once the session is idle, the input field is empty and no dialog, Ask question, permission prompt or menu is open, confirmed twice; it verifies the typed line before pressing Enter and never retypes user input. Autonomous mode: `run --auto` without a question; interactive modes: ask once via the Ask tool, then `run --user-confirmed`. It refuses without the compact-plus rehydrate breadcrumb and outside tmux. After the compact the session wakes itself: the SessionStart hook (source `compact`) signals the finished compaction deterministically, then the worker types `.` (shared wake helper with self-reload, 60 s fallback); without the signal in time it types `.` only into an idle pane, else it sends an ntfy push. Details: `commands/self-compact.md`.

## Periodic reminder (a quality prompt typed into the own tmux pane)

On by default (opt-out). The credo config key `reminder` (global `~/.claude/credo/config`, a profile, or a project `.credo/config`) holds the triggers per credo session mode; the builtin template has these defaults:

```yaml
reminder:
  enabled: true                # false switches the whole reminder off
  text: ""                     # optional one-line override of the built-in text
  active: {turns: 20}          # every 20 real user turns in active mode
  passive: {turns: 20}
  autonomous: {minutes: 60}    # every 60 min in autonomous mode (the user is away, no turns)
  paused: {turns: 20}          # autonomous with keep-alive paused (owner present): turns only
```

Off switches, in any user config layer: `enabled: false` turns the whole reminder off; under a mode, `turns: 0` and `minutes: 0` (or the mode set to `off`) turn that mode off; `paused: {turns: 0}` turns the reminder off while autonomy is paused. Each key merges with the defaults one by one, so `autonomous: {turns: 5}` keeps the default 60 minutes; set `minutes: 0` as well to leave only the turns trigger.

Each reminder is one full turn for the agent (it re-reads the rules, the items, the logs and the handoff), so it costs tokens; autonomous mode can send up to 24 per day per session. `/credo:setup` asks once about the reminder and states this cost. The first reminder of each session carries one extra line that names the switch; later reminders do not.

A mode may set `turns`, `minutes` or both (whichever comes first); a mode without a key, or with both keys 0, is off. `turns` counts real user prompts since the last reminder (or since arming), `minutes` the time since then. Injected reminders, a bare `.` and automated prompts are not turns. The built-in text asks the agent to check itself against what was agreed (rules, open items, requirements logs, handoff, superseded decisions dropped); `text` replaces it after the marker `[credo-reminder]`.

Every real user turn is counted (UserPromptSubmit hook `hooks/credo-reminder.sh turn`). The 10th turn arms the session for good; the state is kept per session id, so it survives a compact and a resume. An armed session has one detached worker (`scripts/credo-reminder.py`, started at SessionStart and on demand). When a trigger is due, the worker types the prompt into the session's OWN tmux pane, but only when the pane is idle, the input field holds fewer than 2 visible characters (such a leftover is removed first, with End and BSpace) and no dialog is open; it verifies the text before Enter. Config changes apply within a minute, and the worker stops when the reminder is off or the session's Claude process is gone. It needs tmux; outside tmux nothing is armed. A user prompt runs the turn counter, except when a shell check finds `enabled: false` in the layer that decides; the config is read only when a worker has to start (`credo-config.sh get reminder`, about 0.1 s). Details: `docs/credo-guide.md`.

## Session move (between profiles)

`/credo:session-move` (`scripts/credo-session-move.py`, skill `session-move`) moves one or more sessions, given by caption / custom title or full id, from one profile (`CLAUDE_CONFIG_DIR`, e.g. `~/.claude`) to another (e.g. `~/.claude-other`). Execution class C: only on the user's explicit invocation, never autonomously, and only from a new session that is not one of the moved ones. It refuses the current session and any live session: a Claude process whose argv names the id (e.g. `--resume <id>`), or a pid file `sessions/<pid>.json` naming the id - in the source, the target or any sibling `.claude*` profile dir or any dir given with `--profile <dir>` (repeatable) - whose pid is alive, whatever the process is called (a dead pid is stale; pid reuse is decided only by the pid file's `procStart` compared with `/proc/<pid>/stat` field 22: mismatch ignored, match / absent / unreadable live, a recognised Claude process never ignored). Without `/proc` (e.g. macOS) it falls back to `ps -axww` (every alive pid from a pid file counts as live); when liveness cannot be determined at all, it refuses. Limit: sessions started with another profile location and Windows-side sessions are not seen unless their profile dir is passed with `--profile`.

- **Captions** resolve from `projects/<slug>/<id>/custom-title.json`, else the newest custom-title record in the transcript - never from the stale `sessions/*.json` pid files. Ambiguous captions are refused; pass the id.
- **Setup detection, not 1:1 copying.** The `plan` (dry run) shows the target layout (top-level symlinks shared with the source vs real entries) and plans each artifact that exists for the id: the transcript, the `projects/<slug>/<id>/` dir (the slug follows the session cwd and can differ per session), and every entry whose name holds the full id (tasks, todos, session-env, file-history, credo / dogma per-session state, mode files, ...). Each item is `COPY`, `PRESENT` (already identical), `SHARED` (the target path resolves into the source through a symlink: already there, never copied, never cleaned up), `CONFLICT` (the target holds something different: stop) or `BLOCKED` (a symlink or special file in the source, a target symlink to a third place, an entry directly at the profile root, or a leftover `<file>.part` from an interrupted copy: never followed, never written through, a `.part` is removed by the user). A session whose files contain symlinks (e.g. subagent files symlinked into another session's dir by an earlier manual move) cannot be moved with this command; the plan says why. Short-id names are listed for review only. Shared logs (e.g. `credo/peer-lan.log`), profile-global config and `plugins/` are never copied.
- **Copy + verify.** One source per explicit target path; each file is written to `<file>.part`, fsynced and hard-linked into place, so nothing is overwritten and no target file is ever half written; no symlink followed, mode and mtime kept. Re-running `copy` after an interruption completes it (identical files are skipped). `verify` reads every file once on both sides (size, sha256, entry count) and, when green, records source and target size + sha256 per file in `<target>/credo/session-move/<id>.json`; refused sessions (live, current, conflict, blocked) get no manifest.
- **Cleanup only by the user.** After the user tested the resume in the target (`cd <cwd> && CLAUDE_CONFIG_DIR=<target> claude --resume <id>`) and explicitly approved it, `cleanup-script --user-confirmed` writes a sh script with literal paths only (new `mktemp` dir under `/tmp`, 0700 / 0600). It refuses while the session is live in any profile other than the target (or liveness cannot be determined), when a manifest item is not part of the session's fresh plan, when the source changed since the verify, or without `sha256sum` / `shasum`. The rule is decided by the source. A source file is removed while it is unchanged since the verify and its target copy exists as a regular file (not a symlink, not empty while the source is not). A target that changed after the copy, the session's transcript included, does not keep the source. A source file whose target copy is missing or emptied is left out (reported as KEPT); a target that is a symlink out of the source blocks the whole cleanup (plan rule). The script removes each file only while it still has the recorded checksum, is not a symlink, and its target copy is a regular file that is not the same file, is not a symlink and is not empty while the source is not (the target's content is not compared); both directories still resolve (`pwd -P`) to the recorded physical directories, and directories only with `rmdir`. It prints `removed N, kept M` and exits 1 when anything was kept. One known limit is that a target that changed after the copy counts as the continuation of the session, so its source goes even when the resume lost content in the target (only an empty target against a non-empty source is kept). A control character in any path refuses the whole script. Titles, slugs and paths from the profile are printed escaped (control / bidi characters as `\xNN`) with a warning. The user runs it with `!`; it is not removed automatically (`rm -f -- '<dir>/cleanup.sh' && rmdir -- '<dir>'`). The agent never deletes.
- The report stays in chat: ids, slugs, every path, the `cd` path, the resume command (plus a launcher alias for that profile if the user has one), and the notes that profiles have separate auth / accounts and possibly launchers with different permission flags, and that project-local `.credo/` handoffs do not move. Details: `commands/session-move.md`, `skills/session-move/SKILL.md`.

## Peer message etiquette

Peer sessions tend to over-communicate: every ack, status note or handoff lands as a new turn, and the receiver often reacts right away (a reply, an immediate commit and push). `credo-peer-message.sh` only informs (the one optional exception is the strict trust guard below):

- **Receiver** (UserPromptSubmit): when the prompt is a `<cross-session-message>`, it injects the handling rule. `[urgent]` (or untagged but asking a question or needing a decision) is handled now; `[info]` and other untagged messages get no reply and no immediate action, and resulting `.credo`/item changes are batched into the next natural commit (idle time, next release, before a compact).
- **Sender** (PreToolUse `SendMessage`): reminds the agent to start the message with `[info]` or `[urgent]`, bundle points, never send pure acks, and end with "No reply needed" when no answer is needed.
- **Autonomy:** a peer message never pauses autonomy (`credo-autonomy-clear.sh` exempts it); only the user's own messages do. Harness notices about other sessions (idle/delivery) are exempt too. A self-scheduled `[CREDO-AUTONOMY-WAKE]` wake that fires after the session left autonomy (switched to active/passive) is dropped by the same hook; the mode commands also stop the wake chain themselves.
- **Trusted peers** (LAN relay): trust is granted per profile, per paired machine and session CAPTION, the name the user set with `/rename`; a grant is made with `trust add` run in that profile and applies only to target sessions of that profile (registry `nameSource` `user`, at most 20 characters); a session without a caption can still message but never holds trust, and while 2+ live sessions on the sending machine share a caption, trust for it is suspended and the hook adds a one-line notice to rename one. The sending relay sends the caption only when the process that wrote the message is that session (or a child of it, checked with `SO_PEERCRED`). When a message carries the receiving relay's trust marker, the hook verifies it (`credo-peer-lan.py trust verify`, local trust list and pairing store, never the message text; the marker counts only in the session it was made for and for 10 minutes). Limits, stated plainly: the caption is what the paired sending relay reports, not a cryptographic proof - a hostile or modified relay on the paired machine can claim any caption and can leave out the duplicate flag (suspension is enforced by the sender's relay); duplicate detection covers every profile of the sending machine; and any process of the same user can read the trust key, so the user account is the trust boundary. `trust add` and `trust list` warn about Latin lookalike characters in a caption (warning only). Verified: the tasks of that session on that paired machine count like the user's own and are carried out without asking, except dangerous ones (deleting user data, installs, money, permission, credential or security changes, the hard safety rules, irreversible steps outside the repo), which are reported to the user. A marker that does not verify adds a warning. The hook recognizes trust grants with a shell-aware parser (`scripts/credo_trust_guard.py`): a Bash run of `credo-peer-lan.py` with `trust` and later `add` (directly, via `python3`, a wrapper or a variable such as `"$P"`), a Bash write to `peer-lan-trust.json` (redirect, `cp`/`mv`/`tee`/`ln`/`dd`, `sed -i`, `rm`, interpreter code naming the file as a path literal) and a Write/Edit/MultiEdit of it. Mentions (read-only commands, commit messages, echo strings, heredoc bodies) are not grants. **Trust guard switch:** by default (`peer.trust_guard.quiet: true`) a grant only gets a non-blocking reminder that only the user grants trust, so autonomous runs with peers are never stopped by a confirmation dialog (a hook "ask" overrides allow rules and bypass mode). Strict mode (`quiet: false`, or env `CREDO_PEER_TRUST_GUARD_QUIET=false`, env wins) makes the user confirm every grant; `/credo:setup` (Step 12) offers it. The key is read from the global and profile layers only (a repo's `.credo/config` cannot downgrade it); without `python3` the config is not read, only the env variable selects strict mode. Strict mode also asks on obfuscated forms (arguments from variables, `$'...'`, brace expansion, globs, `eval`, a trust file name built from pieces). The guard is a best-effort reminder, not a security boundary: the boundary is that only the user runs trust grants. Details: [`commands/peer-lan.md`](commands/peer-lan.md#trusted-peers-local-per-receiving-machine).
- **Disable** with `CREDO_PEER_ETIQUETTE=0`.

## Model presets

credo picks the model and effort for each subagent from a preset. Your main model stays your own choice (`/model`, `/effort`); a preset only recommends one for the main agent.

- **Built-in presets:** `quality` (Opus for build, review and hard work), `balanced` (the default: Haiku for explore, build and review; hard work escalates from Haiku to Opus, then goes back to you), `budget` (Haiku throughout, with one final Opus attempt). The stages and prompts live in `templates/presets.default.yaml`; `scripts/credo-preset.sh show [name]` prints one in full.
- **Select:** `preset: <name>` in the global or project config. The project overrides global; unset means `balanced`. Custom presets go under `presets:` with the same schema, may use any supported model id (claude-haiku-5-5, claude-opus-5-5, claude-sonnet-5-5; an unknown id warns), and a same-named custom preset replaces the built-in one as a whole.
- **Stages:** a role (`explore`, `build`, `review`, `hard`) is one stage `{model, effort, attempts, subagent-prompt}` or a list of stages that may end with `back-to-human`. Effort is low, medium, high, xhigh or max. `attempts` is a positive number or `until-done` (no cap; budget caps and a repeated failure without progress stop it).
- **Chains:** a failed attempt (red tests, a red done-gate, an audit FAIL, or a subagent reporting itself stuck) is retried with its findings; when a stage is used up the next stage takes over, and `back-to-human` moves the item to `1_clarify` with an URGENT note and an ntfy push.
- **Prompts:** `universal-prompt` for every agent, `mainagent-prompt` for the main agent (delivered at SessionStart and after each compaction; `/credo:session-active` and `/credo:session-init` print it once mid-session), `subagent-prompt` per stage (appended by the main agent when it spawns the subagent). A missing key adds nothing.
- **Helper:** `scripts/credo-preset.sh stage <role> [attempt]` prints alias, effort, the prompt block and the next action; `mainagent`, `show`, `list` and `active` cover the rest. Invalid parts print a warning and fall back to `balanced` for that role.
- **Setup:** `/credo:setup` presents the three built-in presets and lets you pick one or describe your own; `/credo:session-init` hints when your main model differs from the recommendation.

Tests: `scripts/test-credo-preset.sh` (helper, validation, config layering, SessionStart injection, doc invariants).

## Parallel work: touches and resource gate

Parallel subagents are wanted: writing builders run 2 to 4 per independent area by default (`builders.min_per_area`, `builders.max_per_area`), and read-only agents have no fixed limit. Two things limit them:

- **File overlap.** An item may carry the optional frontmatter `touches:` - a list of paths or globs it will likely edit, set by the plan / clarify agent at the latest at GO. It is guidance: the main agent re-checks it right before spawning builders and updates it when files moved. `scripts/credo-touches-check.sh [--json] <id> <id> ...` prints overlapping item pairs (glob-aware, conservative) and lists items without `touches:` as `unknown` (exit 0 no overlap, 3 overlap, 4 no project, 1 bad args). Overlapping items run sequentially; `unknown` items are classified by the main agent, parallel by default. Read-only work (research, clarify) stays freely parallel.
- **Resource gate.** `scripts/credo-resource-check.sh [--disk-gb G] [--path P] [--json]` runs before every agent start in every mode and prints `ok` (exit 0) or `wait:<reason>` (exit 5). It compares the 1-minute load per CPU and the used RAM share against `resources.max_busy_percent` (default 90); at or above it no new agent starts. Free disk is checked at every start too: `--disk-gb G` (the item's `disk_gb`; absent = reserve only) plus `resources.disk_reserve_gb` must fit on the drive of `--path`. Unreadable values never block. On `wait` no new agent starts; the main agent re-checks when the next agent finishes (no polling loop).
- **Heavy items.** `heavy: true` (model or benchmark tests, large downloads) never runs in parallel to another heavy item.
- **Disk space.** An item may carry `disk_gb: <GB>`. The start checks `--disk-gb <GB>` plus the reserve on the target drive (`--path`), at every start. Not enough free space: the item stays in `2_go` and is retried later. Autonomous mode sends one ntfy "waiting for disk space" per item.

Config keys (defaults in the builtin template):

| Key | Default | Meaning |
| --- | --- | --- |
| `resources.max_busy_percent` | `90` | no new agent at or above this CPU load per CPU or used RAM share (percent) |
| `resources.disk_reserve_gb` | `3` | free disk that must stay after an item's `disk_gb` |
| `resources.disk_reserve_gb` | `3` | free disk (GB) that must stay after an item's `disk_gb` |

The procedure lives in the orchestration skill; tests: `scripts/test-touches-check.sh`, `scripts/test-resource-check.sh`.

## Worktrees for every code track (setup and cleanup)

Every code track that works in a git worktree goes through this flow, also a single isolated build track, not only parallel ones. Everything below runs automatically - you never have to run a command.

- **Hard rule.** Under `flow=hydra` the Agent tool's built-in `isolation: "worktree"` is never used, and a bare `git worktree add` without the setup script is never run - always hydra's create flow plus its setup. Under `flow=native` every `git worktree add` is followed by the setup script.
- **Which flow.** Before ANY worktree run, `scripts/credo-worktree-flow.sh [--json] [dir]` prints `flow=hydra|ask|native` and the `setup=` script to use. It reads the DOGMA-PERMISSIONS checkbox `use Hydra for 2+ independent tasks` (`### Hydra` subsection) (stable id `§xw1i`) through `scripts/credo-dogma-mode.sh [--id <id>] <subsection> <pattern> [dir]` (matches the id first, anywhere in `<permissions>`, then the subsection + text as fallback for files without ids; prints `auto|ask|deny|missing`, works without dogma, falls back to the main worktree's file; picks the file like dogma - `dir` as the target, else the credo pinned project, else the current folder - and inherits settings the file does not define from the session folder's file (the folder the session was started in, recorded per session by the `credo-session-dir-record.sh` SessionStart hook so it is still found after a `cd <project> && ...`; without a record `$PWD`) unless it says `- [ ] (§r3nx) inherit permissions`): `[x]` or no checkbox / no file (default on) with hydra installed = hydra's create flow, `[?]` = ask the user once per batch (never in autonomous mode: native), `[ ]` or no hydra = native `git worktree add`.
- **Setup.** A fresh worktree only has versioned files, so rules and items are missing. Right after every `git worktree add`, `scripts/credo-worktree-setup.sh <worktree> [main-checkout]` (or hydra's identical `worktree-setup.sh`) links (relative symlinks) or copies the excluded files: the "Worktree files" list of DOGMA-PERMISSIONS.md (`link: <path>` / `copy: <path>`, read via dogma's `worktree-files.sh`), else the default - CLAUDE.md, CLAUDE/, GUIDES/, DOGMA-PERMISSIONS.md and everything unversioned under .credo/, each only if it exists. Only ignored paths are linked or copied: an untracked path that is not ignored in the main checkout (e.g. a new uncommitted item file) is skipped with `skipped <path> (untracked, not ignored - read it in the main checkout)`, because a `git add -A` in the worktree would commit the link and a merge would put it into main; such paths are never added to the shared `info/exclude`. A directory with tracked files inside (or a not-ignored one holding ignored entries) is recursed into and only its untracked, ignored entries are linked; versioned paths are skipped with a warning; an existing path is never overwritten. A linked directory ignored only by a `dir/` pattern gets an anchored `/dir` line in the shared `.git/info/exclude` (a `dir/` pattern does not match a symlink). It prints `main=<main checkout>`, which goes into every builder brief: builders may look up anything missing read-only in the main checkout, never write or commit there.
- **Cleanup at item close and after every release.** Every move to done, verified or archived, and every release, runs `scripts/credo-worktree-cleanup.sh [--dry-run] [--json] [--base <branch>] [--fresh-hours N] [--keep <path|branch>]... [dir]` per the checkbox `clean up merged worktrees automatically` (stable id `§36ch`; `[x]` remove without asking, `[?]` or no checkbox list and ask, `[ ]` never). It removes only worktrees whose branch is merged into the main branch (an ancestor, or every commit patch-equivalent in it after a rebase) and that have no changes at all (no uncommitted changes, no untracked non-ignored files; an untracked symlink into the main checkout, such as a setup link for `node_modules`, is no change) or only `.credo/` changes whose lines all already exist in the same file of the main checkout (lossless: removed with `[x]`; with `[?]` listed as `candidate ... (lossless)` and removed only after your yes, by running the script with `--allow-lossless <branch>` per approved worktree; with `[ ]` kept; a missing or failing setting helper counts as `[ ]`; a real ignored file under `.credo/` makes a worktree dirty) and no live process with their working directory inside, via `git worktree remove --force` (symlinks are unlinked, never followed) and `git branch -d`. A rebased branch that `-d` refuses is kept, and the output gives `owner_command=git branch -D <branch>` for you to run. The main worktree, the current one, locked, `--keep`-named and unmerged worktrees are kept and reported with the reason (locked ones as `kept <path> branch=<b> reason=locked: <lock reason>`, also on `--dry-run`). A merged worktree that is locked, has changes or has a live process inside is an owner question: its report line ends with `(ask owner)`, and the agent asks you instead of removing it. A worktree whose branch has no commit of its own is kept while younger than 24h (a fast-forward from main does not count as a commit of its own). Every run covers all worktrees, so the first one sweeps the backlog.
- **Keeping a worktree (opt-out).** When you tell the agent to keep a worktree, it locks it: `git worktree lock --reason "keep: owner" <path>`. A locked worktree is never removed, by the cleanup script, the auto mode or `/hydra:cleanup`. `scripts/credo-worktree-cleanup.sh --list-locked [--json]` lists the locked worktrees with their reasons (also visible as `locked` lines in `git worktree list --porcelain`); the agent names the kept worktrees before an item close. Release with `git worktree unlock <path>`: in autonomous mode the agent may unlock a `keep: owner` lock itself once the keep reason no longer applies, in every other mode it asks you first via the Ask tool, and it never unlocks a lock with another reason on its own. `--keep <path|branch>` (repeatable) keeps a worktree for a single run without locking.

Tests: `scripts/test-worktree-setup.sh` (credo and hydra setup), `scripts/test-worktree-cleanup.sh` (including the item-move wiring), `scripts/test-worktree-flow.sh`.

## Optimisation audit

`/credo:optimize` (skill `optimize`) is an audit credo offers but never forces. It is language-agnostic and respects the repo's existing conventions: it detects what the repo already does first and recommends an ecosystem standard only where nothing exists, for the user to confirm.

- **Opt-in per repo.** The question is asked once, together with the credo onboarding question (SessionStart ASK), in `/credo:setup` (Step 2c) and in `/credo:session-init`; for a directory where credo is already active, `credo-optimize-hook.sh` asks it on the next fresh start. Nothing is scanned before the answer. Yes = run it now, later offered again only to returners; No = never offered automatically, `/credo:optimize` stays available by hand. The answer is stored per repo and per profile.
- **Only for returners.** `credo-optimize-hook.sh` (SessionStart, also on resume) offers the audit again only when the repo has been idle for at least `optimize.idle_days` (default 7) by wall-clock: credo's own per-repo last-seen timestamp (updated on every prompt by the same hook on `UserPromptSubmit`), the newest reflog entry, the mtime of `.git/index`, and the newest mtime among the files `git status --porcelain` reports as modified or untracked must ALL be older. It is evaluated before last-seen is updated, asked once per return, never in autonomous mode (the offer then stays pending for the next attended session). Silent in `/credo:disable`d directories and with the `gsd` backend. Toggle: `CREDO_OPTIMIZE_HOOK` (default true).
- **Fresh state first.** Before every run, `scripts/credo-optimize-fresh.sh` checks that the repo is on its default branch and not behind its remote (`git fetch` is its only non-read action). If not, the agent proposes `git switch <default>` and `git pull --ff-only` and runs them only with consent; a stale state is never audited silently.
- **Scan (read-only, by a subagent).** Conflict hotspots from `git log` (auto-discovery instead of central registration lists, smaller modules, generated instead of hand-written mirror lists, splitting a growing `CLAUDE.md` into the dogma `CLAUDE/<topic>.md` + `GUIDES/` pattern with fixed `@`-paths); changelog fragments (a versioned `changelog.d/` assembled by `/dogma:versioning` at the release commit, never a tag); the test-stage convention; dogma settings inferred from the workflow (Test Commands stages, the release-only option, the Hydra checkboxes - passed as suggestions to `/dogma:permissions`, credo holds no dogma logic); parallelism readiness (worktree files list, large files that block parallel work). Opt-in extra, asked separately: instruction consistency (read-only check of the global and repo instruction files and plugin-injected texts for contradictions with credo).
- **Result.** A report at `.credo/process/reports/optimize-<YYYY-MM-DD>.md`, and every finding offered as Implement / Later / Never. Accepted larger findings become credo items, small ones may be done directly after confirmation, and Never is remembered per repo and finding.

Scripts: `credo-optimize-state.sh` (opt-in, last-seen, pending offer, last-offer, never-list; `get --json`), `credo-optimize-idle.sh [--days N] [--json]` (`idle=yes|no` plus the four signal ages; exit 0 idle, 1 not idle, 4 not a git repo), `credo-optimize-fresh.sh [--no-fetch] [--json]` (exit 0 fresh, 1 stale, 3 unknown, 4 not a git repo). State lives under `${CLAUDE_CONFIG_DIR:-$HOME/.claude}/credo/optimize/<repo-hash>/` (linked worktrees share the main checkout's state).

| Key | Default | Meaning |
| --- | --- | --- |
| `optimize.idle_days` | `7` | offer the audit again only when every activity signal is at least this many days old |

Tests: `scripts/test-optimize-state.sh`, `scripts/test-optimize-idle.sh`, `scripts/test-optimize-fresh.sh`, `scripts/test-optimize-hook.sh`.

## Wait-loop hint

`credo-wait-hint.sh` (PreToolUse Bash) adds a hint when a command loops on `pgrep -f` (`until ! pgrep -f "X"` matches the waiting shell's own command line and never ends): wait on a result file or one specific PID with a time limit, or rely on the harness completion notification. It never blocks; the rule itself is in the orchestration skill. Disable with `CREDO_WAIT_HINT=0`.

## Claude Code band (optional)

When credo runs inside Claude Code with mods support, `hooks/band.tsx` (listed under `modules` in `hooks/hooks.json`) draws a small band above the prompt. It is optional: it only reads credo's state through the core scripts above and renders it. The core - hooks, scripts, skills, items - works exactly the same without it and in harnesses without mods.

- **Counts line** - `◆ credo` plus the item count per status (`cf go bk`, `dd vf`, `pk ar`), colored per group, zero counts dimmed. Changes flash for 6 s (fuchsia for moves, white for new items) with a toast. Without a credo project (no item system, also in a pinned project without items) the counts and the item controls (`i`, `l`, `e`) are left out, but the session line - mode/role, open test, question and veto codes, `h` help - and the autonomy line still show whenever there is something to show (also in a declined directory or without a credo mode: only the item system is off there); the prompt hint then lists the shorthands that work without items (`cf dd vf ??? ?? ? cm ph`) and the `h` cheatsheet leaves out the `#N` item moves.
- **Session line** - this session's mode/role (`autonomous paused/task` when a user message paused the autonomous run; pausing and re-arming flash the tag like an item move), the open test, question and veto codes (🧪 / ❓ / ✋, vetos in bold yellow) from the footer of the last answer, and the controls: `i` items pane, `h` shorthand cheatsheet (both in one shared pane, from `credo-item-list.sh` and `templates/shorthands.json`), `l` short/long labels (`go: 12` vs `Go(go): 12`), `e` rotates the presets `all` / `no parked` / `open + dogma` / `open only` (`open only` also hides the dogma band).
- **Autonomy line** - only while this session runs autonomously: `⟳ auto` with the 5h utilization, the next ladder rung and the next wake time.
- **Self-restart notice** - only while a self-restart of this session is pending: a yellow `⚠` and blinking fuchsia `credo self-restart in m:ss (reason: ...) - cancel: credo-self-restart.py cancel` on top of the band (gone within a second of a cancel, relaunch or failure), plus ONE standing toast `credo self-restart at hh:mm:ss ...` that stays until the restart (a cancel adds a short "cancelled" toast) (`hooks/self-restart-marker.ts` reads the `self-restart.json` marker).
- **Prompt hint** - `Shortcuts: ...` lists the shorthands the band does not show (long form `key(word)` follows `l`).
- `/credo-items` opens the items pane too. It refreshes on session start, after Bash calls, at turn end and every 10 s.

## Remote mirror (optional, off by default)

Set `remote.mirror_command` in the global or profile config to a shell command. A repo's `.credo/config` is ignored for this key on purpose: it is a security default, so a repository cannot switch the mirror on or point session events at a command of its own. Keep it that way. credo then sends one JSON event per owner blocker to that command on stdin, in the background, with a 5 s timeout and no output read back:

- `ask` - an Ask-box question (`PreToolUse` on `AskUserQuestion`): the questions, options and `multiSelect`.
- `permission` - a permission dialog (`PermissionRequest`): tool name and a summary (the command, or the file path; file content is never sent). A subagent origin is marked. A summary beyond 2000 characters is cut at a word boundary and the event then carries `cut: true`. Every permission event carries `sha256`, the SHA-256 hex digest of the full unmasked command, so the exact command can be matched without being sent; `masked: true` marks a summary that the masking changed.
- `question_codes` - a question heading `### ❓ Q<n>) <topic>` in the final reply of a turn (the footer is not a source). Carries `text`, see below. A legacy single-letter heading `### ❓ B) <topic>` (older sessions) is sent too, with the letter as `code`; since letters are reused, it is deduplicated together with its topic. The same holds for `test_blocking`.
- `test_blocking` - a test heading `### 🧪 T<n>) <topic> [blocking]`. A test without the marker is not sent. Carries `text`, see below.
- `blocker` - a line `Blocker: <what only the owner can solve>` (or `**Blocker:**`). `Blocker: none`, `-` or empty is not sent. Carries `text`, see below.
- `remote_reply` - the final reply to a message that started with `[remote chat <id>]` (`<id>`: letters, digits, `.`, `_`, `-`). `text` is the whole reply up to 1 MiB (1048576 UTF-8 bytes); a longer one is never cut silently: it is shortened at a word boundary, ends with `[truncated: N of M characters, limit 1 MiB]` and the event carries `cut: true`. The same limit applies to `command_reply`. Masking and sending run in the background, a long string is masked in blocks of 200 lines.
- `command_reply` - the final reply to a raw slash command (`<command-name>/NAME</command-name>` in the last owner prompt, for example typed from the app without the remote chat prefix). Carries `command` (`/NAME`, with a plugin prefix when there is one), `text` (the final reply, see the 1 MiB limit below) and `prompt_ts` (the timestamp of the command prompt, when the transcript has one). Skill bodies (`isMeta` entries) never count as the owner prompt. A prompt with the remote chat prefix stays a `remote_reply`.

`text` on `question_codes` and `test_blocking` is the block below the heading: its lines up to the next code heading (`### ❓`, `### 🧪` or `### ✋`), the next markdown heading of the same or a higher level, or the end of the reply, trimmed. Lines inside a fenced code block are text, so a `#` comment inside a code block does not end the block. The field is always present and may be empty. A block longer than 4000 characters is cut at a word boundary, and the event then carries `cut: true`; a block that fits has no `cut` key. `heading` is unchanged.

`context` on `question_codes` and `test_blocking` is the reply text above the heading: from the start of the reply, or from the end of the block of the previous code heading, up to the heading, trimmed and fenced-aware. It is omitted when nothing is above the heading. Longer than 4000 characters it keeps its END (the text right above the heading): the last 4000 characters, starting at a line boundary (or after the partial word when there is no line break), and the event carries `context_cut: true`. A code heading inside a fenced code block is not an event.

`text` on `blocker` is the text of the Blocker line (without the prefix) plus the lines below it, trimmed and masked like every string. The block ends at the next markdown heading (any level), the next code heading (`### ❓`, `### 🧪` or `### ✋`), the next `Blocker:` line or the end of the reply; lines inside a fenced code block do not end it. It is capped at 4000 characters at a word boundary, and a longer block carries `cut: true`. The cap is applied before masking, so a masked `text` can be longer than 4000 characters. A run of token characters with no space in it is never sent partly: when no word boundary is left, its trailing token characters are dropped, and the text may then be empty. Before this contract `text` held only the Blocker line, cut at 1000 characters without a mark. A Blocker line of up to 1000 characters gives the same first line as before; a longer line is no longer cut there, so a consumer that reads only `text` keeps working and now also gets the context.

Before anything is sent, every string of the event is masked (`hooks/credo-remote-mirror-redact.jq`, rules in its header): auth headers and Bearer tokens, `NAME=value` and `NAME: value` for token, secret, password, key and credential names, `--password`, `--token` and similar flag values, `-p` values of mysql, psql, sshpass, mongo and redis-cli, `user:password@` in URLs, provider token prefixes (`ghp_`, `github_pat_`, `xox*-`, `sk-`), and runs of 32 or more letters and digits (hashes, base64 secrets). A masked part shows as `***`. The `sha256` field is set by the hook and is not masked. Known trade-off: a full 40-character commit hash is masked too. If the masking fails, nothing is sent.

Every event carries `type`, `session_id`, `cwd`, `ts` (UTC) and its own fields (ask and permission events add `subagent`, and `agent_type` when set); no status or veto events are ever sent (a block's `text` can quote the lines below a blocker, which may include a status line or the open-codes footer), and the only digest is `sha256` of a cut permission command. The same open question is sent once per session (Ask by `tool_use_id`, codes by code, a blocker by its Blocker line, a permission prompt once per 10 minutes). The hooks never print a decision, never block and always exit 0; a failing sink is ignored. Test: `scripts/test-credo-remote-mirror.sh`.

## Dependencies

credo works on its own. Three touchpoints are external:

### `limit` plugin - recommended prerequisite

The [`limit`](https://github.com/Marcel-Bich/marcel-bich-claude-marketplace/wiki/Claude-Code-Limit-Plugin) plugin is a prerequisite for two features:

- **Context-percent triggers** - the auto-run of compact-plus at the configured session-context fill thresholds relies on the limit plugin's inject hook. Point it at credo with:
  - `CLAUDE_MB_LIMIT_COMPACT_SKILL=credo:compact-plus`
  - `CLAUDE_MB_LIMIT_INJECT_THRESHOLDS=80,92`
  - `/credo:setup` offers to set these for you (Step 9) when the limit plugin is installed, so hand-editing is optional.
- **Budget data source** - the budget skill reads the limit cache (`/tmp/claude-mb-limit-cache_*.json`) for the 5-hour and weekly utilization and reset times.

If the `limit` plugin is absent, these features are silently unavailable. There is no error; credo simply does not run the budget or auto-compact logic that has no data.

### tmux (strongly recommended)

Run Claude Code inside [tmux](https://github.com/tmux/tmux). Several credo features type into the session's OWN terminal pane, and only tmux gives them a pane they can safely inspect and type into:

- **`/credo:self-compact`** - tmux only. Outside tmux it refuses and you compact by hand.
- **`/credo:self-reload`** - tmux only (types `/reload-plugins` and `/reload-skills` into the own pane).
- **Periodic reminder** (`reminder` config key, on by default) - tmux only (types the reminder prompt into the own pane); off with `reminder.enabled: false`.
- **`/credo:self-restart`** - works without tmux (new Windows Terminal tab / terminal window), but only inside tmux it waits until the pane is idle with an empty input field, so a prompt you are typing is never lost, and relaunches in the same pane.

This fits WSL too, because tmux runs inside the WSL distro like on any Linux and the Windows Terminal tab is just the window around it. Native Windows has no tmux - use WSL.

`/credo:setup` (Step 11) detects whether tmux is installed and whether the current session runs inside it, shows the exact install command for your package manager (apt, dnf, pacman, zypper, brew) and runs it only after your explicit yes. It can also add a small `ctmux` shell function (bash, zsh or fish, again only after a yes) that always starts Claude Code inside a named tmux session and re-attaches to it if it already exists:

```bash
ctmux() { if [ -n "$TMUX" ]; then claude; else tmux new-session -A -s "${1:-claude}" claude; fi; }
```

When credo is active and a session starts outside tmux, the SessionStart hook adds one short line recommending tmux. It stays silent after you declined tmux in `/credo:setup` Step 11 (stored as `tmux.hint: false` in the credo config), in non-terminal hosts (`CLAUDE_CODE_ENTRYPOINT` other than `cli`) and with `CREDO_TMUX_HINT=false`.

### `ntfy` - optional

Push notifications use `ntfy`. The topic is a personal field in the credo config (`personal.ntfy_topic`). If it is unset, ntfy is silently skipped; nothing else changes. Progress is bundled into a digest on a fixed interval (`ntfy.digest_interval_minutes`); when a topic is set, sending it is mandatory whenever there is progress (with no topic it stays silently skipped), and every finished item is one line naming it and one sentence of what was done (`#N <title>: <what was done> (<version>)`, the version once released). Meta information (mode, budget, session) appears only when it concerns the owner, such as a decision, a blocker or the power-down. Messages are written in the owner's configured language with umlauts. One message is preferred, split into `n/m` when it would exceed ntfy's size limit.

## Installation

Add the marketplace and install `credo`, or copy the plugin into your `.claude-plugin/` location. Then run `/credo:setup` to initialize a project and, optionally, pre-fill config. Starting Claude Code inside tmux is strongly recommended (see [tmux](#tmux-strongly-recommended)); setup helps install it.
